# Wanderfile product evolution roadmap

## Product direction

Wanderfile is an AI-organized library for content saved from social media and
the web. A saved item can become a useful, structured object: a place on a map,
a recipe, a movie or series in a watchlist, or a searchable post with extracted
details.

Travel remains a supported content type, but it is not the identity of the
whole product. The existing place atlas, visit history, maps, and route tools
remain specialized views within the broader library.

The initial rebrand deliberately keeps internal identifiers such as the Python
package name, AWS stack names, mobile bundle IDs, URL scheme, `travel` category
key, and `/travel` routes. Keeping them stable avoids data, deployment, and deep
link migrations. User-facing labels use **Wanderfile**, **Places**, and
**Visits** instead.

## Current product

The application currently provides:

- Link and share-to-app ingestion for supported social and web sources.
- A searchable saved-post library.
- AI classification into one primary content category.
- Specialized extraction and browsing for places, recipes, and movies/TV.
- Place maps, visit history, and travel-specific routing tools.
- Post filters for categories that do not yet have specialized extraction.

`SavedPost.content_category` currently has one job: choose the primary topic and
route the close pipeline. It must remain a single value while the pipeline uses
that contract. See [pipeline-framework-design.md](pipeline-framework-design.md).

## Rollout principles

- Preserve the current visual system and make product changes incrementally.
- Keep pipeline routing separate from library organization. No field should
  carry both intents.
- New product behavior is feature-flagged and defaults off until validated.
- AI output should be editable, explainable, and easy to override.
- Existing saves, links, routes, and deployments must continue to work during
  each rollout phase.

## Phase 1: neutral product foundation

Status: implemented as the first branding pass.

- Standardize the visible product name as **Wanderfile**.
- Replace global travel-planner messaging with saved-library messaging.
- Present Travel as **Places** and History as **Visits** in navigation.
- Use neutral save, bookmark, library, and AI language in onboarding and ingest.
- Keep travel terms where they describe an actual travel feature.

Follow-up polish:

- Review app-store listing text and screenshots before the next native release.
- Replace any travel-specific marketing artwork that remains outside the app.
- Validate the new onboarding copy with users who save non-travel content.

## Phase 2: multi-label AI organization

Add organization metadata without changing the single-value pipeline routing
field.

From a user's perspective, this is **multiple categories per saved item**: one
post can appear under food, Seattle, date night, and budget-friendly at the same
time. Internally, those memberships should be represented as topics and tags;
`content_category` should not become an array because it selects exactly one
close pipeline.

Suggested fields on a saved post:

- `topics`: broad subjects such as cooking, travel, fashion, or home design.
- `entities`: people, products, places, titles, ingredients, or other named
  things found in the content.
- `ai_tags`: descriptive labels generated by the system.
- `user_tags`: labels explicitly created or applied by the user.
- `summary`: a concise, general-purpose summary of the saved item.
- `action_items`: useful actions such as cook, watch, buy, read, or visit.

`content_category` must continue to mean only the primary pipeline category.
The new fields must not determine pipeline identity implicitly.

Potential feature flags:

- `ai_organization_metadata`
- `ai_tag_suggestions`

Initial UI work:

- Show AI tags and extracted entities on post details.
- Add topic and tag filters to the existing library toolbar.
- Let users add, remove, and correct labels.
- Visually distinguish AI suggestions from user-authored organization.

## Phase 3: collections

Introduce collections as a user-owned organization layer.

Examples include "Weeknight dinners," "Movies to watch," "Seattle ideas,"
"Summer outfits," and "Small-space inspiration."

Minimum data model:

- A user-scoped collection ID, name, optional description, and timestamps.
- Explicit membership records between collections and saved posts.
- Membership origin (`user` or `ai_suggested`) as its own field.
- Optional acceptance state for AI suggestions.

First release:

- Create, rename, and delete a collection.
- Add or remove a post manually.
- Browse the posts in a collection.
- Suggest likely collections after ingest, with accept and dismiss controls.

Later improvements:

- Merge and reorder collections.
- Collection cover images and pinned collections.
- Bulk organization from the post library.
- Shared or collaborative collections, only after private collections are
  stable.

Potential feature flags:

- `collections`
- `ai_collection_suggestions`

## Phase 4: semantic search and discovery

Expand search beyond literal title and caption matching. Users should be able
to ask for concepts such as:

- "Quick vegetarian dinners"
- "Movies recommended by this creator"
- "Things I saved for Seattle"
- "Haircuts for curly hair"
- "Small apartment storage ideas"

Search may use summaries, topics, entities, AI tags, structured extraction, and
collection membership. The system should return the matching evidence and not
present inferred details as source facts.

Potential feature flags:

- `semantic_search`
- `related_saves`

## Phase 5: category-specific experiences

Add specialized extraction only where it creates a clearly better experience
than the generic post view.

Possible candidates:

- Fashion: garments, brands, colors, seasons, and outfit components.
- Hair: style, length, texture, color, maintenance, and reference images.
- Home: room, style, materials, products, and project ideas.
- Shopping: products, variants, price snapshots, and purchase intent.
- Learning: concepts, resources, steps, and a read/watch queue.

Each category should follow the pipeline framework: reusable steps in the step
library, category-specific close pipelines, and product behavior behind feature
flags until validated.

## Future information architecture

The current tabs remain during the rebrand to minimize UI disruption. Once
collections exist and non-travel categories have richer experiences, evaluate
the following navigation:

```text
Home
Library
  All saves
  Places
  Recipes
  Movies & TV
  Fashion
  Hair
  Other
Collections
Search
Add
```

Visits can then live within Places or the user profile. This navigation change
should be driven by actual collection usage rather than bundled into the
branding release.

## Success criteria

- New users understand that they can save more than travel content.
- Existing travel users can still find maps, places, visits, and routes.
- Users can understand why an item was categorized or suggested.
- Corrections improve organization without changing the ingest pipeline's
  routing meaning.
- Search and collections reduce the time required to find a previously saved
  item.
